# テスト

テストは**仕様を満たしていることを保証するガード**として書きます。
実装を変えたときに仕様からずれたら、テストが失敗して気づける状態を保ちます。

## テストピラミッド

```
        ▲  e2e          少ない・遅い・本物の AWS
       ▲▲▲ integration  部品の組み合わせ（辞書、HTTP 層、S3 など）
      ▲▲▲▲▲ unit        多い・速い・純粋な関数
```

| ディレクトリ        | 対象                                                 | 実行                    |
| ------------------- | ---------------------------------------------------- | ----------------------- |
| `test/unit/`        | I/O を伴わない純粋な関数（入力検証、正規化、n-gram） | `pnpm test:unit`        |
| `test/integration/` | kuromoji の辞書、Hono の HTTP 層、Floci 上の S3/SSM  | `pnpm test:integration` |
| `test/e2e/`         | デプロイ済みの Dev 環境の Function URL               | `pnpm test:e2e`         |

`pnpm test` は unit と integration を実行します。e2e は AWS の認証情報とデプロイ済みの環境が必要なので、明示的に実行したときだけ動きます。

### どの層に書くか

- 境界値や組み合わせの多い検証は、ロジックを純粋な関数に切り出して **unit** で網羅する
- **integration** では、部品をつないだときの振る舞い（ステータスコード、レスポンスの形）を代表的なケースで確認する。unit で確認済みの境界値を繰り返さない
- **e2e** では、本物の環境でしか確認できないこと（IAM 認証、Lambda の初期化、S3 の権限）だけを確認する

## 仕様のガードとして書くためのルール

1. **テスト名は仕様の文章にする**：「何を入力すると、どうなるか」を日本語で書く。テスト名を並べると仕様書として読める状態にする
   - 良い例：`1000 文字ちょうどは受け付ける`
   - 悪い例：`parseTokenizeRequest のテスト`、`ケース 3`
2. **実装ではなく振る舞いを検証する**：内部の関数呼び出しや変数ではなく、入力と出力（公開された関数の戻り値、HTTP のレスポンス）を見る。実装を書き換えても仕様が同じならテストは通り続ける
3. **境界値は両側を書く**：上限なら「ちょうど」と「1 つ超え」の両方
4. **仕様を変えるときは、先にテストを変える**：テストを失敗させてから実装を直す。テストを実装に合わせて書き換えるのは、仕様の変更を意図したときだけ
5. **期待値は具体的に書く**：`toBeTruthy()` よりも `toEqual({ ... })` で値そのものを書く
6. **ガードとして効くか確かめる**：新しいテストを書いたら、実装をわざと壊してテストが失敗することを確かめる。壊しても通るなら、そのテストは仕様を守れていない
