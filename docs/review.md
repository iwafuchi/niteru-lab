# セルフレビュー

PR を作る前に、次のループを指摘がなくなるまで繰り返します。

```
実装 → ① pnpm check → ② セルフレビュー → 指摘があれば修正して ① に戻る
                                         → 指摘がなければ PR を作る
```

1. **`pnpm check`**：整形の確認・Lint・型チェック・テスト・`cdk synth` をまとめて実行する。失敗したら直して最初からやり直す
2. **セルフレビュー**：差分全体（`git diff main...HEAD`）を下の観点表で読み直し、あわせて Claude Code の `/code-review` で不具合を探す

PR の「確認したこと」には、`pnpm check` の結果と、セルフレビューで見つけて直したことを書きます。見つからなかった場合も「指摘なし」と書きます。

## 観点表

各項目の「過去の例」は、このリポジトリで実際に PR の後や作業の途中で見つかった問題です。同じ漏れを繰り返さないための観点として残しています。

### 仕様とテスト

- [ ] 振る舞いを変えたなら、仕様のテストを先に書き、実装前に失敗することを確かめたか
- [ ] 新しいテストは、実装をわざと壊すと失敗するか（壊しても通るテストは仕様を守れていない）
  - 過去の例：ひらがなをカタカナにする処理を外しても全テストが通った
- [ ] わざと壊して確かめた後、実装を元に戻したか（git の管理外のファイルは `git checkout` で戻らない）
  - 過去の例：確認の途中で 1 行が消えたまま残った
- [ ] 新しい仕様が既存のテストと衝突していないか。衝突したら、既存のテストの意図を変えずに直したか

### コミットと PR

- [ ] 1 つのコミットに、別の目的の変更が混ざっていないか（`git show --stat` で確認する）
  - 過去の例：型情報を使う Lint の設定が、機能追加のコミットに混ざった
- [ ] コミットメッセージの本文に、理由と判断が書いてあるか。その理由は根拠として十分か
  - 過去の例：zod-validator を見送った理由が、設定で解決できる問題だった
- [ ] 判断を後の工程でも参照するなら、`docs/decisions/` に記録したか

### セキュリティ

- [ ] 認証情報やアカウント固有の値（アカウント ID、API キー）をコード・コミット・PR に書いていないか
- [ ] IAM の権限、Function URL の認証、公開範囲を広げていないか。広げたなら理由があるか
- [ ] Floci では確かめられない設定（IAM 認証など）を、テンプレートのテストで守っているか
- [ ] 新しい依存は、バージョンとチェックサム（またはコミット SHA）で固定し、公開から 7 日以上たっているか
- [ ] 新しく実行するツールが、外部にデータを送る設定（テレメトリー）になっていないか。送るなら無効にしたか
  - 過去の例：CI で cdk synth を実行するようにした際、CDK の CLI のテレメトリーが標準で有効だった

### ドキュメント

- [ ] コマンド、ディレクトリ構成、手順を変えたなら、README・docs・CLAUDE.md を更新したか
- [ ] Markdown の相対リンクが切れていないか
